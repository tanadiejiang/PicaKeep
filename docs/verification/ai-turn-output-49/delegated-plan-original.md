# 48 · 修复 AI 多次清单展示后的空回复提示气泡

## 任务目标

保留每次有效工具调用即时展示独立清单的能力，修复“本轮已有清单，却在结束时追加（AI本轮未返回有效内容）”的错误提示。收尾判断依据本次用户提问已经实际展示的内容；临时缓冲区消费完毕不代表本轮没有输出。

## 当前理解的用户意图

用户希望单条清单展示正常，多次清单仍能分别展示。工具已有明确的零结果或失败说明时，保留具体反馈；只有本轮确实没有可用展示内容和具体终局反馈时，才使用现有轻量空回复提示。

用户此前要求等主会话处理完其他内容后再交付，现已于 2026-10-02 明确回复“ok，现在可以了”。本计划可以交付主会话执行。

## 执行范围

- 修复 `AiConversationController` 中即时清单展示与最终空正文判断之间的状态衔接。
- 增加仅在运行时保存、按一次用户提问隔离的展示摘要，保留跨工具子轮及下载确认暂停/恢复的连续性。
- 保留自动展示工具白名单：`display_result_list`、`search_by_image`。
- 明确同一次调用的重复展示与不同调用的独立展示边界，保护工具调用和结果在 `_history` 中的配对。
- 补充控制器与必要的 Widget 回归测试，核对相关历史存储和工具协议测试。
- 实施后在本计划追加执行结果；主会话如有统一交接流程，仅同步本项实际改动及未验收事项。

用户明确示意交付后，由主会话安排执行。执行者先核对当前工作区和同文件并行改动，读取本计划涉及函数及调用方，再更新状态为“执行中”。不重置其他任务的改动，不因文件行号移动而机械套用旧位置。

先运行能复现本问题的定向用例并保存基线。旧用例调用 `simulateToolCallRoundForTesting` 时默认 `continueWithLlm: true`，可能继续进入真实 LLM 请求；手动提供最终回复的测试必须显式传 `continueWithLlm: false`。生产工具循环测试使用已有 `chatRequestForTesting` 注入脚本回复，避免实际模型、账号、网络状态影响结果。

### 2. 按一次用户提问记录展示摘要

在控制器内部增加最小运行时状态，或等价的私有结构。至少能区分：

- 本轮已实际追加的有效清单卡数量；
- 本轮已经保留的非空 assistant 正文或思考展示；
- 本轮已经展示的具体零结果说明、明确失败原因或既有终止反馈；
- 本轮收尾是否已经完成，以及需要时用于隔离旧异步回调的回合标识。

新用户提问和新会话初始化时重置；历史恢复后不能把旧消息算成正在进行的一轮。一次用户提问中的多个工具子轮、等待下载确认及确认后续跑共享本轮状态，不重新清零。已结束轮次的回调不得污染下一轮摘要或再次追加兜底。

优先在实际追加/保留展示消息的位置记录状态。工具调用开始、转圈、泛化“工具执行成功”、只有原始 JSON 的中间结果，均不能自动证明用户已得到可用输出。具体零结果或失败反馈须已进入既有用户可见消息通道；不能仅因存在任意 `toolResult` 就跳过收尾判断。

### 3. 保留即时出卡，明确重复处理边界

白名单工具成功且条目有效时，仍立即生成独立 `resultList`。先确认卡片已追加，再记录本轮展示状态；最终 flush 不应重复生成已经展示的卡片。

不同调用即使返回完全相同的作品，也各有一张卡。同一次调用的相同结果被重复交付时最多展示一次。如确有重复回调入口需防护，使用本轮标识、工具子轮和调用实例位置组成的身份；非空 `toolCallId` 可参与标识，不能只用原始 ID 建全局集合。空 ID 或下一子轮复用 ID 不得吞掉新调用，失败后的修正重试也不得被先前失败标记阻断。

不引入无依据的全局工具执行去重。展示防重不能改坏 `_history`：每个已记录的 assistant tool call 必须有正确配对的 tool result；不能只跳过历史写入或把不同调用合并。若已有单一 flush 路径足够保证幂等，保留简单实现，并用重复收尾测试证明，不为本修复引入完整调度框架。

### 4. 调整最终收尾判断

正文非空时保持原文展示和入历史行为；清单卡与正文可以同时存在。正文为空时先沿用流式气泡封口逻辑，再根据本轮实际展示摘要判断：

| 本轮状态 | 结束行为 |
| --- | --- |
| 至少一张有效清单 | 保留全部清单；不追加“AI本轮未返回有效内容”。 |
| 已保留非空正文或流式思考 | 保留原展示；不因最终正文为空追加泛化空回复。思考展示沿用既有历史契约。 |
| 没有清单，但已有具体零结果反馈 | 保留具体反馈，不再添加一条同义或泛化提示。 |
| 没有清单，但已有明确失败/终止反馈 | 保留原因及现有重试、终止语义，不追加泛化空回复。 |
| 没有以上输出，仅工具状态或完全空白 | 只追加一次现有轻量提示，且不写入 `_history`。 |

保留异常、用户停止、最大工具轮数到达时现有的收尾逻辑；这些分支不额外补本次泛化提示。对 `_pendingDisplayItems` 的全部写入、flush 和清空位置作一次完整核对，禁止再次依赖“消费后的缓冲区是否为空”判定本轮输出。

## 风险或注意事项

- `AiChatMessage.toolResult` 的“工具执行成功”是默认文案，不等于已展示结果。只设置 `hasAnyToolResult` 会掩盖“搜索成功但没有清单/答案”的另一类静默失败。
- `_sealStreamingMessage` 的返回值与真实流式消息是否存在有关；仅注入 `reasoningContent` 不能假装验证过真实流式封口。测试需驱动同一封口路径。
- 一个用户回合包含多个工具子轮，下载确认只是暂停点；状态不能在每次 `_runLoop` 或工具结果到达时重置。
- 运行时摘要不持久化，不扫描整份旧历史来判断本轮；结束时记录终止状态，新回合才重新初始化。
- 防重只解决同一次调用的重复交付；不得吞掉不同调用或失败后的合法重试，不得产生孤儿 tool call/tool result。
- 如果执行时发现共享代码已改变了以上诊断前提，先说明差异再调整实施安排，不能直接套用旧行号或覆盖他人改动。
- 项目构建只允许 debug/profile；本修复优先用定向测试和静态分析验证，不需要自动打包或安装。若后续另行安排设备验证，须核对 APK 存在、显式设备 ID 并保留应用数据；禁止 release、卸载、清空数据。

- 本轮执行边界：覆盖了什么；未覆盖什么及原因。没有排除时明确写全量覆盖。
- 过程概述：基线、实际实施、验证及必要调整。
- 是否遇到问题：有/无，并说明实际问题。
- 未完成事项：包括暂缓原因及后续验证方式。
- 相关文件或结果位置：源码、测试、日志及实际更新的交接记录。

### 经验层（触发即填；未涉及写“本轮无”）

- 架构决策与理由：本轮状态记录方案及被否决方案的具体理由。
- 接口/行为契约：每次调用独立清单、展示防重、历史配对、用户回合/工具子轮边界及破坏后的表现。
- 根因推理链：实际症状、排除项和证据；诊断前提与实施发现有差异时明确写出。
- 踩坑与不要重复的路径：缓冲状态误用、任意工具状态抑制兜底、跨调用误去重、测试误走真实 LLM 等实际发现。
- 技术约束：来源及证据强度，区分用户/项目约束、已验证结论与推测待验。
- 模块职责演变：新增或改变职责时以“文件 | 原职责 | 本轮后职责 | 迁入迁出”记录。
- 残余风险/未验证假设：前提、若不成立的后果、验证方法，尤其是流式、取消、暂停恢复和设备界面未验收项。
- 跨轮诊断模式（可选）：本轮实际验证出的可复用结论。
